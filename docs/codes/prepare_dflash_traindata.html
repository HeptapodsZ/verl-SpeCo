DFlash 训练数据准备：old-logprob hidden capture 路径

本文围绕一条主线解释：如何在 actor 的 old-logprob forward 中选择并采集 target model hidden rows，如何把它们恢复成按 rollout 样本组织的数据，再如何对齐出 DFlash 可消费的 ids / h_states / masks。分析范围仅覆盖当前工作区的 old-logprob hidden capture 路径，不把 SGLang rollout capture、EAGLE3 或 DSpark 分支混入结论。

源码版本本地提交 7f1e1f7；以当前工作树为准
证据方法rg -n、nl -ba、静态调用链核对
运行验证未启动模型训练；本文不声称 GPU / Ray 运行时实测
核心结果默认 513 hidden rows → 514 token/mask slice → 512-row DFlash window

二、步骤 1：_speco_build_oldlogprob_collect_plan

Role（4 句话）

该方法负责判断本 RL step 是否应从 old-logprob forward 采集 DFlash 训练特征。它从 rollout batch 的 attention/response mask 得到每个样本的真实 prompt 与 response 长度，再按采样率、owner 容量和 token 配额筛选样本。对每个入选样本，它生成连续的 hidden_positions，并记录该样本应发送到哪个 drafter owner。它输出的是“采集计划”，不直接生成后续的 ids、hidden_states 或 loss_mask。

关键细节 1：启用条件与路径约束

已验证事实old-logprob capture 是 opt-in，且与 SGLang capture / logits 路径互斥
speco_ray_trainer.py:868–905 
collect_hidden_states_from_old_logprob
collect_hidden_states_from_sgl == false
use_logits == false
actor.strategy in {"fsdp", "fsdp2"}

基础 YAML 默认没有启用该路径，但将 capture 实现预设为 forward_hook： speco_base.yaml:49–64。

关键细节 2：为什么计划采 513 行而不是 512 行

已验证事实hidden_rows = train_rows + 1
speco_ray_trainer.py:1147–1154

train_rows 优先读取 hidden_state_window_tokens_per_sample，未配置时才回退到 hidden_state_window_min_rows；实现见 speco_ray_trainer.py:949–953。基础配置两者均为 512，因此当前默认计划的 R = hidden_rows = 513；配置证据见 speco_base.yaml:62–64。

已验证事实front 模式从 prompt 最后一项开始；random 模式在 response 范围内偏移

三、步骤 2：old-logprob forward hook

Role（4 句话）

forward hook 的职责是在 actor 本来就要执行的 old-logprob forward 中旁路截取 target model 中间层输出。runtime 根据 collect plan 将样本内序列位置转换为 packed/local tensor 索引，并只保留入选样本的目标 rows。它在配置指定的 target context layers 上注册 hook，forward 结束后把各层结果沿 hidden 维拼接。最终结果被写入 old-logprob 输出；若 ObjectRef 路径可用，还可转换成 Ray 引用以避免把大 tensor 直接嵌入返回对象。

关键细节 1：计划元数据如何进入 forward

已验证事实trainer 在 compute_log_prob 前写入四类采集元数据和 layer/layout 设置
speco_ray_trainer.py:2204–2227

batch_td[HIDDEN_POSITIONS] = collect_plan["hidden_positions"]
batch_td[HIDDEN_POSITION_MASK] = collect_plan["hidden_position_mask"]
batch_td[OWNER_RANK] = collect_plan["owner_rank"]
# 另附 aux_layer_ids、capture_impl、hidden_layout

DFlash-family 的布局解析结果是 dflash_aux，表示训练侧消费 target auxiliary context layers，而非 EAGLE3 的 aux+last 布局；实现见 oldlogprob_layer_ids.py:76–93。如果无法从显式 DFlash layer ids、drafter checkpoint 或 target config 解析 layer ids，trainer 会拒绝猜测并抛错；见 speco_ray_trainer.py:1083–1106。

四、步骤 3：_speco_collect_oldlogprob_features

Role（4 句话）

该方法位于 controller 侧，负责把 old-logprob worker 返回的“按 batch 组织的 hidden 结果”恢复成“按 rollout 样本组织的训练 payload”。它同时兼容直接 tensor、单个 Ray ObjectRef 和 chunked ObjectRefs 三种 hidden 载体。它依据原 batch 的 mask 去掉 prompt/response padding，并把完整 token 序列、hidden positions、layout 和 hidden 数据封装在同一个 sample 中。最后按 collect plan 的 owner_rank 分 bucket，通过 owner-route RPC 送往 drafter workers。

五、步骤 4：collect_online_data

Role（5 句话）

该方法把 worker 收到的 rollout sample 转换为可缓存、可抽样的 drafter training item。它先把 input ids、hidden positions、hidden states 以及 prompt/response 等 tensor 搬到 CPU，以降低长期占用训练设备显存。随后以 hidden_positions 为 source of truth，检查连续性并计算 hidden slice 与 token slice 的共同对齐窗口。它在完整 prompt+response 上构建 response-only loss mask，再用同一个 feature_start:feature_end 切出局部 ids 和 mask。最终 item 被写入跨 step 的 DataBuffer 或当前 step 的 collected_data。

六、步骤 5：preprocess_individual_items

Role（4 句话）

该方法是通用 collection item 到 DFlash backend 输入之间的最后一层 per-sample 预处理。它把 token、hidden 和 loss mask 搬到 DFlash 训练设备，并强制验证 hidden layout 与 target context hidden 宽度。它将三者截到共同有效长度，然后围绕第一个 loss-active response 位置裁出不超过 dflash_max_window 的窗口。返回值是三个列表：ids、h_states 和 masks，供后续 per-sample chunk/packing 逻辑使用。

关键细节 1：layout 与 hidden width 是 fail-closed 校验

已验证事实DFlash 只接受 None 或 dflash_aux

关键细节 3：为什么取三者最小长度

已验证事实代码只保留 token、hidden、mask 的公共前缀
dflash_trainer_backend.py:1108–1111 
valid_len = min(ids.size(0), full_h.size(0), item_loss_mask.size(0))
ids = ids[:valid_len]
full_h = full_h[:valid_len]
item_loss_mask = item_loss_mask[:valid_len]

代码推断 取最小值的直接效果是防止后续逐 row 组合时任一 tensor 越界，并建立共同的行数不变量；代码未附带“为何选择截断而非报错/补齐”的设计说明。对当前正常 old-logprob 样本，进入此处通常是 ids=[H+1]、full_h=[H,D]、mask=[H+1]，所以公共长度是 H；这一 shape 由 base_trainer.py:2611–2626 的 +1 token window 与 base_trainer.py:2858–2863 的切片共同推出。

关键细节 4：围绕首个 response loss row 裁窗

已验证事实窗口以第一个非零 mask 为参照，并受 dflash_max_window 限制

基础配置的 dflash_max_window 是 512，见 speco_base.yaml:108–115。预处理结果随后被读取为 ids_list / hidden_list / mask_list，进入 DFlash 的 per-sample chunk/packing 阶段；见 base_trainer.py:3395–3424。

代码推断 对默认 front window，局部 token slice 从原序列位置 p−1 开始；完整 loss mask 在 prompt 区域为 0、response 区域为 1，因此局部 mask 通常以 [0,1,1,…] 开头。第一个非零位置通常是 1，512 窗口的 start 会 clamp 到 0，所以默认正常样本最终取公共 513 行中的前 512 行。该结论依赖“response 无内部 padding、front 模式、有效长度足够”三个条件；mask 构造见 base_trainer.py:2695–2705，裁窗公式见 dflash_trainer_backend.py:1112–1122。

八、事实、推断与尚未验证的边界
